# MXMT Analytics — інструкція користувача

Оновлено **30 жовтня 2026 року**. Основний робочий процес тепер проходить через **Огляд → Продажі → Склад → Переоцінка / Дозамовлення**. Додаткові модулі збережено в меню **Інші інструменти**.

Нижче описано можливості поточної реалізації. Фактична доступність залежить від ваших прав, підключення, погоджених правил і повноти даних. Підготовлений код не означає, що джерело клієнта, платний AI або зовнішня дія вже активовані.

## 1. Вхід і навігація

1. Відкрийте `/login` і введіть свої email та пароль. Новий окремий кабінет створюється на `/register` з назвою бізнесу, ім’ям, email і паролем від 8 символів.
2. Поточний login/register відкриває **Дашборд** (`/dashboard`). Для нового MVP виберіть **Огляд** у меню.
3. На вузькому екрані відкрийте **Меню**. Основні розділи, дії й Налаштування доступні в тому самому порядку.
4. Перемикач теми пропонує «Світла», «Темна» та «Як у системі» і зберігає вибір у браузері. Без збереженого вибору використовується системна тема. UA/EN змінює мову в адресі сторінки й запам’ятовує її для наступних відкриттів. Для завершення сесії натисніть **Вийти**.

Кабінети різних бізнесів ізольовані. Якщо сесія завершилася, увійдіть повторно; не передавайте пароль, cookies або API keys для діагностики. Передайте адміністратору URL, час, дію та requestId, якщо він показаний.

### Ролі

| Роль | Основні можливості нового MVP |
| --- | --- |
| VIEWER | Перегляд звітів, previews і дозволеної історії; без генерації/завантаження scenario CSV |
| ANALYST | Додатково scenario CSV та evidence-backed AI за наявності policy; legacy перерахунок звітів |
| ADMIN / SUPER_ADMIN | Додатково підключення, мапінги/approval, вибір джерела, імпорт, MVP projection та клієнтські налаштування |

Окремі API мають власні role/evidence gates. Сервер перевіряє доступ незалежно від видимості кнопки; приховане меню не змінює права. `SUPER_ADMIN` не є способом підставити чужий tenant у звичайний запит.

## 2. Як отримати дані на п’яти екранах

Наявність рядків у **Дані та звіти** ще не означає готовність MVP. Потрібні послідовно: **завантажене джерело → погоджені правила → вибране джерело MVP → опубліковані спільні факти → розрахунок/snapshot**.

### Google Sheets / Zavod

Перший запуск виконує адміністратор:

1. У **Налаштування → Загальне → Google Sheets цього кабінету** збережіть посилання на погоджену таблицю. Для приватної таблиці надайте сервісному акаунту платформи доступ на читання. Збереження не запускає імпорт і не змінює джерело MVP. Новий кабінет не успадковує глобальну таблицю. Перед імпортом у **Дані та звіти** перевірте посилання **Наступний імпорт**. Раніше імпортовані дані залишаються історією та не змінюються від збереження підключення.
2. Відкрийте **Інші інструменти → Дані та звіти → Google Sheets** і виконайте raw-імпорт. Якщо повідомлення каже, що MVP-мапінгу ще немає, перевірте збережені raw таблиці: цей етап може вже бути успішним.
3. У **Налаштування → Загальне** знайдіть мапінг Google Sheets. Виберіть збережене джерело та зіставте реальні колонки каталогу й замовлень.
4. Підтвердьте значення статусів, валюту, одиниці/суми рядка, ID товару/замовлення/рядка, дати оплати й повернення та час спостереження залишку. Підказка за назвою колонки не є погодженням правила.
5. Запустіть preview, перевірте counts і зауваження. Дублікати/неоднозначність не виправляються автоматично вибором першого збігу. Погодьте точний preview окремою дією з reference лише після перевірки правил.
6. У картці **джерела MVP-звітів** явно виберіть це Sheets-джерело. Погодження мапінгу не вибирає його автоматично.
7. Поверніться до **Дані та звіти** й виконайте **Оновити MVP-звіти / Refresh MVP reports**. Кнопка працює зі збереженим імпортом, створює спільні факти й запит на перерахунок; нового Google download не робить.
8. Відкрийте **Огляд** і перевірте джерело, період, свіжість, coverage та попередження. Перевірте всі п’ять екранів і потрібні деталізації.

Після налаштування наступний **Імпортувати** на сторінці Sheets виконує raw save, окрему MVP-проєкцію для вибраного Sheets і окремий legacy calculation. Повідомлення розрізняють ці результати. Якщо raw збережений, а інший крок failed, не треба вважати всі дані втраченими або бездумно повторювати весь pipeline.

**Важливо:** daily Google import не запускає MVP-проєкцію автоматично. Після нового scheduled raw import потрібен явний MVP refresh. Зміна структури/мапінгу може вимагати нового preview та approval. Старі результати можуть зберігатися як історичні, але не позначаються поточними після зміни входів.

Для реального Zavod потрібно окремо погодити source identity, статуси, amounts/currency, дати, ownership і правила залишків. Поточна динамічна таблиця не доводить значення на дату старого ТЗ; відсутня історія не відновлюється з поточного залишку.

### SalesDrive

1. ADMIN відкриває **Налаштування → Загальне → SalesDrive**, вводить read credentials та потрібні account/feed mappings у захищену форму.
2. Збережіть і перевірте підключення. Підтвердіть account-specific statuses, оплати/повернення, currency/amount semantics, каталог і доступні receipts.
3. Явно виберіть перевірене джерело у картці **джерела MVP-звітів**. Збереження credentials саме по собі його не перемикає.
4. Запустіть потрібний history/catalog import або refresh у controls синхронізації. Дочекайтеся завершення jobs та фінансового перерахунку; факт постановки в чергу не означає готовність звіту.
5. Відкрийте п’ять екранів за потрібний період. Для автоматичного продовження оператор має підключити external worker; наявність коду cron не доводить, що worker уже працює.

Залишки й ціни накопичуються лише за фактичними спостереженнями. Завантаження поточного YML не створює історичний closing stock. Неповний backfill може дозволяти частину даних, але LY, velocity або інші показники залишаться unavailable.

### CSV, KeyCRM, Horoshop і Shopify

Форми onboarding є у **Налаштування → Загальне**. Для remote provider потрібні його permissions, реальні mappings, check, явний вибір джерела та import. Account readiness перевіряється окремо для кожного магазину.

Для CSV завантажуйте UTF-8 файли з явними колонками, перегляньте preview і активуйте конкретний пакет. Каталог, датований stock, order lines і receipts мають окремі правила. Неповний пакет не очищає відсутні товари й не засвідчує повну історію. CSV не опитується за розкладом.

Одночасно звіти використовують одне вибране джерело; дані CRM, магазину й Sheets не додаються одне до одного автоматично.

## 3. Спільні фільтри й читання показників

На п’яти екранах блок **Що потрібно для повних звітів** пояснює відсутній залишок, історію надходжень, швидкість продажів, власність і тип товару. Лічильники стосуються всього джерела в обраному знімку, незалежно від фільтрів екрана. Порожня Переоцінка або відсутність рекомендацій не доводять відсутність неліквіду чи дефіциту, якщо класифікація недоступна. Без допустимих SKU фінансові підсумки уцінки показані як недоступні.

Група без підтвердженої валюти або залишку може містити історичні SKU, відсутні в останньому каталозі. Їхня історія зберігається; невідомий поточний залишок не прирівнюється до нуля. Для активації надходжень із додаткової вкладки Zavod потрібне окреме погодження типів документів, факту приймання, дат, ціни/валюти, прив’язки товарів та унікальності рядків. Наявність вкладки сама по собі не активує імпорт.

Угорі MVP-екранів виберіть місяць, квартал, рік або довільний період та канал, потім натисніть **Застосувати**. Редагування незастосованої форми ще не змінює звіт. URL зберігає applied filters; ним можна повернутися до того самого контексту за наявності доступу.

Період за замовчуванням: 1–6 числа — попередній повний місяць; із 7 числа — поточний місяць до вчора. Поточний незавершений день не додається до завершених sales windows. Майбутній або некоректний період відхиляється.

Канал обмежує продажі. **Залишки — за всіма каналами**, що пояснено над звітом. При переході з KPI на деталі зберігайте snapshot, валюту, період і потрібний population. Увесь stock не дорівнює автоматично піднабору кандидатів на переоцінку.

| Показник / стан | Як читати |
| --- | --- |
| Виручка / GP | Повернення й corrections враховуються за погодженою політикою; покритий GP не є повним, якщо частина costs невідома |
| LY | Порівняння з відповідним минулорічним періодом; без достатньої історії не підміняється нулем |
| Velocity / WOH | Серверна швидкість продажів і тижні покриття; використовуються history/exposure evidence, а не проста різниця двох видимих колонок |
| STR | Коефіцієнт проданих одиниць у підтвердженій receipt-cohort; потребує відповідної історії |
| Availability | Частка активних SKU в наявності; невідома активність/stock може робити точний ratio недоступним |
| Немає даних / unavailable | Бракує доказів або валідного знаменника; це не нуль і не доказ відсутності проблем |
| Partial | Показана відома частина; перевірте кількість/причини непокритих рядків |

Валюти не сумуються. Свіжі дані можуть мати неповну історію. Вік товару, receipts, transit, ownership і commission не виводяться з назви бренду або дати завантаження файлу.

## 4. Огляд

**URL:** `/overview`.

Огляд містить O1–O8 KPI, підсумки й пріоритетні дії. Натискайте доступні показники для переходу в Продажі, Склад, Переоцінку або Дозамовлення з відповідними фільтрами.

Перевіряйте валюту, план/період, completeness та warnings перед висновком. Якщо класифікація неповна, система не повинна показувати непідтверджені «0% неліквіду», «дефіциту немає» або однозначний головний bottleneck. Відомі проблеми можуть бути показані навіть за неповного загального охоплення.

## 5. Продажі

**URL:** `/sales`.

Використовуйте S1–S4 для перегляду продажів за місяцями, каналами, категоріями та товарами. Змінюйте доступні виміри гроші/одиниці, metrics, sorting, search і pagination. Порівняння LY має власну coverage та той самий погоджений scope.

Загальні підсумки рахуються сервером за повною відфільтрованою сукупністю, а не сумою поточної сторінки. Відсутні costs не дозволяють назвати covered GP повною маржею. Для розбіжності з Оглядом спочатку звірте snapshot, dates, currency і drill-down population.

## 6. Склад

**URL:** `/stock`.

K1–K4 показують якість/структуру запасу, категорії, бренди та SKU. Доступні переходи до відповідних дій. У monobrand-кабінеті основний аналіз переходить на категорії/SKU; це налаштування, не окрема версія застосунку.

Історія складу показує лише реальні observations вибраного набору. Пропущений день не є нульовим stock; observation не оголошується залишком рівно на 23:59. Ретроспективна valuation використовує відомі на той момент ціни/собівартість, а не сьогоднішню картку товару.

Переходи до DEAD/RISK/HEALTHY та інших статусів використовують збережені правила й precedence. Не переносіть старі thresholds з Дашборду, Аналітика або Календаря на новий MVP автоматично.

## 7. Переоцінка

**URL:** `/repricing`.

1. Перевірте snapshot і scope, виберіть статус, бренд/категорію та інші фільтри R1. За замовчуванням відбираються DEAD-кандидати.
2. Налаштуйте sliders, доступну мету, тривалість та інші параметри R2. Значення перераховує сервер.
3. У R3 перевірте кожний SKU та за потреби введіть ручну ціну. Дотримуйтеся cost-floor/маржинальних обмежень; liquidation потребує явного дозволеного рішення.
4. Дочекайтеся актуального preview. Під час запиту або помилки попередній total не є підтвердженим новим результатом.
5. Звірте R4: обрані рядки, нові ціни, знижки, тривалість і суми. Експортуйте лише готовий сценарій із потрібними правами.

Поточний export-контракт обмежує eligible own-stock UAH rows. Невідомі власність/cost або неприпустимі ціни можуть блокувати рядки. Reset очищає edits і повертає defaults; новий snapshot або source change потребує нового preview.

Ручна ціна змінює сценарій, **не ціну в CRM**. Live SalesDrive write-back зараз не підключений.

## 8. Дозамовлення

**URL:** `/reordering`.

1. Виберіть режим дефіциту/ризику або конкретний бренд; для brand mode спочатку вкажіть бренд.
2. Перевірте lead time, post-delivery coverage і MOQ. Порожні overrides використовують збережені supplier terms; client fallback явно позначається.
3. Перегляньте stock, velocity, days-to-zero, transit і рекомендовані units. Якщо transit невідомий, введіть підтверджену кількість або явно підтвердьте нуль. Не підтверджуйте нуль лише для розблокування експорту.
4. Перевірте notes та exclusions. Off-season/нульові/непридатні рядки не стають purchase recommendations.
5. Звірте підсумки повного сценарію та групи **постачальник + валюта**. Підтверджені supplier terms і costs потрібні для export.
6. Експортуйте весь готовий сценарій або конкретну готову supplier/currency group.

Зміна scope, режиму або snapshot може очистити тимчасові transit confirmations; перевірте їх повторно. Перехід між сторінками не змінює загальні серверні суми. Live-відправлення постачальнику зараз не активоване.

## 9. CSV та журнал дій

Scenario export доступний ANALYST/ADMIN/SUPER_ADMIN; VIEWER переглядає дозволену історію без download. Експортується весь обраний готовий scope, а не лише видима сторінка.

| Файл | Колонки |
| --- | --- |
| Repricing | `sku;barcode;brand;category;name;old_price;new_price;discount_pct;promo_days;reason` |
| Reordering | `supplier;sku;barcode;name;qty;unit_cost;sum` |

Формат — UTF-8 із BOM, роздільник `;`. Для Reordering файли відокремлені за supplier/currency. Перед ручним імпортом у зовнішню систему звірте identifiers, leading zeros, кількості, ціни, валюту й правила цієї системи. CSV creation не підтверджує зміну ціни чи надходження товару.

Журнал показує автора, час та exact saved artifacts; повторне завантаження не створює нову дію. Якщо відповідь export загубилася, використовуйте штатний retry поточного сценарію, а не багато нових спроб. Змінився сценарій — спочатку новий preview.

## 10. Settings і Data Quality

### Загальне

Бізнес-бриф, reporting-source picker, Sheets mapping, SalesDrive/KeyCRM/Horoshop/Shopify/CSV onboarding, sync/progress/Data Quality, legacy Google Drive sync і глобальний AI provider.

Data Quality відокремлює **поточні винятки товарів** від **історії попереджень імпорту**. Відкрийте групу для переходу до SKU й джерела проблеми: невідомий бренд/тип, category/cost/retail, ownership, commission, supplier terms, receipt або transit. Один SKU може входити в кілька груп, тому суми груп не слід додавати. Після виправлення alias/type/mapping може знадобитися re-import/reprojection; саме збереження settings не переписує всю історію.

Legacy Google Drive **Синхронізувати** живить старі модулі. Це інша дія, ніж raw import і **Оновити MVP-звіти**. Перемикач Google Sheets/SalesDrive у Data & Reports також не перемикає source picker у Settings.

### Мерчандайзинг

`/settings?tab=merchandising` містить клієнтські правила, mono/multibrand, primary brand, monthly plans/currency, thresholds/quarantine, статуси/exclusions, ownership/commission, suppliers/MOQ/lead/coverage і seasons категорій.

SKU overrides мають пріоритет над brand defaults; inheritance не тотожне явному UNKNOWN. Unverified supplier terms можуть давати provisional preview, але блокувати export. Нові source statuses не вважаються підтвердженими лише тому, що їх запропонувала форма.

Зміна rules може вимагати нового import/replay і snapshot. При конфлікті revision перечитайте актуальні settings і повторно перевірте зміни, не перезаписуйте їх навмання.

### Агенти

Provider per agent задається для існуючих дев’яти agents. Server provider keys налаштовує оператор; CRM keys вводяться тільки у призначені connector-форми. Не вставляйте жодні secrets у AI-чат, reference поля або коментарі.

## 11. AI та підготовлені v2-функції

MVP chat використовує збережений snapshot, серверні fact cards і посилання на докази. Новий запит потребує ANALYST+ та окремого погодженого AI budget. Відсутність policy або коштів не обходиться зміною provider у браузері. При зміні source/settings почніть із нового актуального контексту; AI-порада не змінює authoritative facts і не виконує закупівлю.

Marketing briefs v2 і custom-label exports мають API/service контракти, але не означають нові готові робочі екрани чи публікацію реклами. Labels змінюють лише явно погоджені слоти; порожні значення не призначені для очищення поточних labels. Перевірка ручного provider import залишається обов’язковою.

Аналіз attributes потребує реальних reviewed samples і словника. External market evidence потребує обраного джерела/ліцензії/бюджету. New-product analog forecast поки готує draft policies та перевірки; активація правил відкладена. Ці можливості не слід представляти як уже підключені клієнту.

Retrospective APIs фіксують підтверджене фактичне виконання exact exported subset; файл export сам по собі не є execution evidence. Відправлення, прийняття замовлення та підтверджене надходження — різні події. GMROI — позначене наближення за реальними daily own-stock observations, не доведений causal uplift.

Зовнішня зміна цін і supplier delivery мають підготовлені preview/approval/audit contracts, але **live transport вимкнений**. Немає автоматичного price write, order send або повторного send після невизначеного timeout.

## 12. Інші інструменти та старі звіти

| Розділ | Поточна роль |
| --- | --- |
| Дашборд `/dashboard` | Збережені legacy KPI/алерти та sync context; не заміна нового Огляду |
| Агенти `/agents` | Дев’ять legacy workflows: Inventory, Channel, Attributes, Repricing, Reordering, Commercial Marketer, Calendar, Campaign Analysis, Weekly Report |
| Агент Аналітик `/analyst` | Окрема legacy класифікація й чат; thresholds не є автоматично правилами MVP |
| Асортимент `/assortment` | Каталоги постачальників, budgets/cart/planner, окремий upload workflow |
| Календар `/calendar` | План подій і legacy рекомендації; запис події не доводить реальний запуск кампанії |
| Дані та звіти `/data-reporting` | Raw таблиці й legacy розрахунки, плюс окремий запуск MVP projection для Sheets |

Google Sheets view має Product YML 2.0 і ZAVOD_API raw вкладки та ARTICLE REPORT / BY BRAND / BY CATEGORY розрахункові вкладки. Legacy formulas й hardcoded source assumptions не слід використовувати як підтвердження нового status mapping або числової звірки MVP.

**Оновити** перечитує status/table; **Імпортувати** читає файл і запускає незалежні кроки; **Перерахувати** перераховує legacy tabs і для ADMIN намагається оновити MVP projection; **Оновити MVP-звіти** працює лише з уже збереженим import для вибраного Sheets. ANALYST зберігає legacy calculate permission, але не ADMIN projection approval.

Для legacy agents звіряйте dependencies, період і trace перед повторним запуском. Новий v2 usage budget не мігрує їх автоматично. Старий симулятор або export у Google Sheets не є новим audited scenario CSV чи фактом зовнішнього виконання.

## 13. Щоденний workflow і помилки

Рекомендована послідовність: перевірити source/progress/Data Quality → оновити відповідний шлях даних → перевірити готовність розрахунку → застосувати фільтри → пройти Огляд/Продажі/Склад → перевірити scenario preview → вручну перевірити CSV та журнал.

| Повідомлення / ситуація | Що робити |
| --- | --- |
| Джерело не вибрано | ADMIN перевіряє reporting-source picker у Settings |
| Потрібна перевірка підключення | Перевірити account access, connection і credentials у відповідній формі |
| Потрібен mapping | Завершити preview/approval реальних Sheets rules |
| Потрібен import / MVP projection | Виконати відповідний import/refresh; raw таблиці самі не відкривають MVP |
| Дані змінилися / snapshot застарів | Оновити звіт і перебудувати preview; старий export зберігається як історичний artifact |
| WARNING | Переглянути issues та вплив на scope; це не загальний дозвіл ігнорувати проблеми |
| FAILED | Зберегти час/code, перевірити окремі raw/projection/calculation outcomes; звернутися до оператора |
| Немає LY, WOH, history або export | Перевірити coverage, verified receipt/stock/cost/terms/transit; не заповнювати відсутнє нулями |
| Повторити / Оновити на екрані | Перечитує report context; не імпортує файл, не погоджує mapping і не перемикає source |

Daily Sheets window заплановано на 07:00–07:59 `Europe/Kyiv`, але це не гарантує успіх cron або свіжий MVP. Remote sync залежить від окремого worker та provider limits. Якщо heartbeat/імпорт не рухається, передайте оператору час, source і видиме повідомлення; не натискайте refresh безперервно.

Під час приймання реального клієнта окремо потрібні source-owner approval, dated benchmarks, однаковий KPI/detail scope та UAT на п’яти екранах. Успішні автоматичні тести або merge PR не замінюють це приймання.
